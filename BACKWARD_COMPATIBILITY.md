# Backward compatibility

The local application has an Angular `/data` page, `/api/catalog`, `/api/import-jobs`, a worker probe command and forward-only PostgreSQL migrations. These are local application contracts, not published third-party APIs.

Migration 005 adds catalog job, membership and current-pointer tables without deleting source identities, import chunks or EOD history. It seeds an existing EODHD symbol list as a `legacy` current version. `GET /api/catalog` keeps its existing fields, but `rows` and `count` now refer to the published current membership. It adds a catalog version and latest-refresh status; the Angular page sends the version on later pages and reloads after publication. Any local script that treated this endpoint as a list of every identity ever seen must instead query retained history from the database or wait for a dedicated historical API. The rollback path for the schema is a coordinated pre-migration database and response-file backup with the prior application image.

For future contract changes, list the consumers and migration path here. Review the consuming side in the same PR when it is available.

Migration 006 adds append-only EOD coverage reports/rows and a transactional input revision counter. It does not change existing catalog or import-job response shapes, source identities, manifests or bar revisions. `GET /api/coverage` is a local endpoint consumed by Angular `/data`; no older API consumer exists. The report counts only committed local EOD observations. Roll back by restoring the coordinated pre-migration PostgreSQL and response-file backup with the previous application image; do not drop the new tables on an active archive.

Migration 007 removes the unused expectation-scope column from current coverage reports and advances the report revision. The local `GET /api/coverage` and `GET /api/catalog` responses omit expectation fields; coverage also omits provider-availability fields and calendar-interval findings. Angular is updated in the same release and uses a new display-cache key. Old immutable report rows remain internal audit data; API responses filter retired findings even if an old report is served during a refresh failure. Existing imported bars, manifests and catalog identities are preserved. Roll back with a coordinated pre-migration backup and the prior application image.

Migration 008 adds `dividends` and `splits` to the existing import-job and manifest data-class checks, plus a per-chunk data class defaulted to `daily_bars` for all existing rows. The EOD job request and `GET /api/import-jobs` latest-job response retain their prior semantics for Angular `/data`; action jobs are addressable by ID but do not replace that EOD status. Existing EOD bars, chunks and manifests are preserved. The new action-revision tables are append-only. Roll back only by restoring the coordinated pre-migration PostgreSQL and response-file backup with the prior application image; do not drop action tables on an active archive or discard their raw files.

If snapshot migration 010 already exists when migration 008 runs, the action table also joins its archive-generation counter. When migration 008 runs first, migration 010 adds that column and trigger later. Either order preserves the action revisions already imported with baseline generation 1.

The same two-way migration handshake adds the snapshot-to-action foreign key regardless of which migration is first. Existing action revisions remain append-only.

The internal action reader returns retained declaration, record and payment dates alongside the existing revision evidence. Provider responses are stopped at 5 MB before buffering the full body; an oversized action response fails without publishing a manifest, while oversized EOD responses retain the prior `invalid_depth_payload` error code.
