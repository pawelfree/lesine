# Platform technology decision — 2026-11-04

- Date, owner: 2026-11-04; accepted by the owner.
- Status: active. The owner accepted Angular, NestJS, PostgreSQL as primary database and canonical market-history store, a first TypeScript DSL/backtest engine outside the API process, checksummed original provider responses, and local Docker Compose operation. The 08:30 service target applies while the Mac is running; missed work is reconciled on startup and labeled late.
- Context: Lesine starts as a private local application and is intended to grow into an investment research platform with many declarative indicators, historical validation, durable market history and scheduled daily results.
- Decision: Use a TypeScript monorepo. Angular serves the browser UI. NestJS serves a versioned API; a separate NestJS process imports market data, evaluates the restricted JSON/DSL and runs historical tests. PostgreSQL stores instruments, canonical dated observations and revisions, immutable indicator definitions, job state, results and run metadata. Keep original provider responses as checksummed local files with manifest records in PostgreSQL. Docker Compose runs the local services. Serve the built Angular UI and `/api` from one loopback origin; expose neither PostgreSQL nor worker ports. Persist PostgreSQL and provider-response files across container restarts. The worker reconciles missed sessions on restart and marks results late when computed after the 08:30 cutoff.
- Why: PostgreSQL supports transactional state, indexing, JSONB and partitioning for historical tables. TypeScript allows shared validation contracts across UI, API and worker. A separate worker keeps imports and historical tests away from request handling. NestJS provides modular application contexts; Angular provides routing and typed forms for research screens and future indicator editing.
- Consequences: PostgreSQL and response files require coordinated backup, restore and schema migrations. The DSL evaluator must remain deterministic and versioned. Local scheduling cannot guarantee 08:30 delivery while the computer is off; an always-on host would require a separate deployment decision.
